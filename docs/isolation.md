# Isolation lab: two sessions, real output

Generated by `npm run lab:isolation` against PostgreSQL 16.15.
Everything below is real output from two live sessions (**A** and **B**). Wallet `4` ("main") starts with **100000 paise (Rs 1,000)**.
Each `A>` / `B>` line is exactly what you would type into that session's `psql`; do the same in two terminals to see it yourself.

## Case 1: READ COMMITTED (the Postgres default)

Question: A reads a balance, B changes it and commits, A reads again. Does A see a different value?

```
A> BEGIN;
BEGIN

A> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 100000 
(1 row)

B> BEGIN;
BEGIN

B> UPDATE accounts SET balance = balance - 30000 WHERE id = 4;
UPDATE 1

B> COMMIT;
COMMIT

A> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 70000  
(1 row)

A> COMMIT;
COMMIT

```

**Answer: yes.** Inside ONE transaction A read 100000, then 70000. Each *statement* gets a fresh snapshot of whatever is committed at that moment (a "non-repeatable read"). For money this means: anything you read and then act on is stale unless you lock it.

## Case 2: REPEATABLE READ

Same steps, but A opens its transaction with `ISOLATION LEVEL REPEATABLE READ`.

```
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN

A> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 100000 
(1 row)

B> BEGIN;
BEGIN

B> UPDATE accounts SET balance = balance - 30000 WHERE id = 4;
UPDATE 1

B> COMMIT;
COMMIT

A> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 100000 
(1 row)

-- A now tries to act on what it saw (spend Rs 100 from its stale view):
A> UPDATE accounts SET balance = balance - 10000 WHERE id = 4;
ERROR:  could not serialize access due to concurrent update
(SQLSTATE 40001)

A> ROLLBACK;
ROLLBACK

```

**Answer: no, A keeps seeing 100000** (one snapshot for the whole transaction). But the lesson is the last step: when A tries to *write* a row that B changed after A's snapshot, Postgres refuses with `could not serialize access due to concurrent update` (SQLSTATE 40001). The database protects you from a lost update, at the price of an error your code must catch and retry.

## Case 3: SERIALIZABLE, two sessions read a balance then write based on it

```
A> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN

B> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN

A> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 100000 
(1 row)

B> SELECT id, balance FROM accounts WHERE id = 4;
 id | balance
----+---------
 4  | 100000 
(1 row)

-- both decided "100000 - 30000 = 70000" from the value they read, and write that number:
A> UPDATE accounts SET balance = 70000 WHERE id = 4;
UPDATE 1

B> UPDATE accounts SET balance = 70000 WHERE id = 4;
-- ...B is BLOCKED: it is waiting for the other session

A> COMMIT;
COMMIT

-- B's waiting statement finishes:
ERROR:  could not serialize access due to concurrent update
(SQLSTATE 40001)

B> ROLLBACK;
ROLLBACK

```

**Answer: B fails** with `could not serialize access due to concurrent update` (40001). Without it, both transactions would have believed they spent Rs 300, yet the balance would have fallen by Rs 300 only once: a classic lost update, where one spend silently disappears. B must roll back and retry from the start (it will then read the new balance).

### Case 3b: write skew (the anomaly REPEATABLE READ does NOT stop)

Rule both sessions enforce in code: "a user's wallets must always hold at least Rs 1,000 in total". The user has wallet 4 (100000) and wallet 5 (100000). Each session checks the total, then drains a *different* wallet.

**REPEATABLE READ:**

```
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN

B> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN

A> SELECT sum(balance) AS total FROM accounts WHERE user_id = 1;
 total 
--------
 200000
(1 row)

B> SELECT sum(balance) AS total FROM accounts WHERE user_id = 1;
 total 
--------
 200000
(1 row)

-- 200000 >= 100000, so each thinks it is safe to drain ONE wallet:
A> UPDATE accounts SET balance = 0 WHERE id = 4;
UPDATE 1

B> UPDATE accounts SET balance = 0 WHERE id = 5;
UPDATE 1

A> COMMIT;
COMMIT

B> COMMIT;
COMMIT

A> SELECT sum(balance) AS total_after FROM accounts WHERE user_id = 1;
 total_after
-------------
 0          
(1 row)

```

**SERIALIZABLE:**

```
A> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN

B> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN

A> SELECT sum(balance) AS total FROM accounts WHERE user_id = 1;
 total 
--------
 200000
(1 row)

B> SELECT sum(balance) AS total FROM accounts WHERE user_id = 1;
 total 
--------
 200000
(1 row)

-- 200000 >= 100000, so each thinks it is safe to drain ONE wallet:
A> UPDATE accounts SET balance = 0 WHERE id = 4;
UPDATE 1

B> UPDATE accounts SET balance = 0 WHERE id = 5;
UPDATE 1

A> COMMIT;
COMMIT

B> COMMIT;
ERROR:  could not serialize access due to read/write dependencies among transactions
(SQLSTATE 40001)

A> SELECT sum(balance) AS total_after FROM accounts WHERE user_id = 1;
 total_after
-------------
 100000     
(1 row)

```

**Answer:** under REPEATABLE READ both commit and the total ends at 0, breaking the rule (no row was written by both, so there is no "concurrent update" to detect). Under SERIALIZABLE Postgres notices the read/write dependency cycle and aborts one session with `could not serialize access due to read/write dependencies among transactions` (40001).

## Case 4: REPEATABLE READ with a JOIN

Does the guarantee still hold when the query joins two tables? A runs a join of `accounts` and `users`; B changes a balance, renames the user and adds a new wallet, then commits.

**REPEATABLE READ:**

```
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN

A> SELECT a.id, a.balance, u.name FROM accounts a JOIN users u ON u.id = a.user_id WHERE u.id = 1 ORDER BY a.id;
 id | balance | name    
----+---------+----------
 4  | 100000  | Lab User
 5  | 100000  | Lab User
(2 rows)

B> BEGIN;
BEGIN

B> UPDATE accounts SET balance = balance - 30000 WHERE id = 4;
UPDATE 1

B> UPDATE users SET name = 'Renamed User' WHERE id = 1;
UPDATE 1

B> INSERT INTO accounts (kind, user_id, name, balance) VALUES ('USER_WALLET', 1, 'phantom', 5);
INSERT 1

B> COMMIT;
COMMIT

A> SELECT a.id, a.balance, u.name FROM accounts a JOIN users u ON u.id = a.user_id WHERE u.id = 1 ORDER BY a.id;
 id | balance | name    
----+---------+----------
 4  | 100000  | Lab User
 5  | 100000  | Lab User
(2 rows)

A> COMMIT;
COMMIT

```

**Control, READ COMMITTED:**

```
A> BEGIN ISOLATION LEVEL READ COMMITTED;
BEGIN

A> SELECT a.id, a.balance, u.name FROM accounts a JOIN users u ON u.id = a.user_id WHERE u.id = 1 ORDER BY a.id;
 id | balance | name    
----+---------+----------
 4  | 100000  | Lab User
 5  | 100000  | Lab User
(2 rows)

B> BEGIN;
BEGIN

B> UPDATE accounts SET balance = balance - 30000 WHERE id = 4;
UPDATE 1

B> UPDATE users SET name = 'Renamed User' WHERE id = 1;
UPDATE 1

B> INSERT INTO accounts (kind, user_id, name, balance) VALUES ('USER_WALLET', 1, 'phantom', 5);
INSERT 1

B> COMMIT;
COMMIT

A> SELECT a.id, a.balance, u.name FROM accounts a JOIN users u ON u.id = a.user_id WHERE u.id = 1 ORDER BY a.id;
 id | balance | name        
----+---------+--------------
 4  | 70000   | Renamed User
 5  | 100000  | Renamed User
 7  | 5       | Renamed User
(3 rows)

A> COMMIT;
COMMIT

```

**Answer: yes, the guarantee holds in PostgreSQL.** The snapshot belongs to the *transaction*, not to a table or a statement, so both sides of the join (and any rows that would have appeared, "phantoms") stay frozen. In the control run, READ COMMITTED shows the new balance, the new name and the extra wallet.

## Case 5: the fix we actually use, `SELECT ... FOR UPDATE` at READ COMMITTED

B tries to take the row lock while A holds it; B must wait, and when it proceeds it reads the *fresh* balance.

```
A> BEGIN;
BEGIN

A> SELECT id, balance FROM accounts WHERE id = 4 FOR UPDATE;
 id | balance
----+---------
 4  | 100000 
(1 row)

B> BEGIN;
BEGIN

B> SELECT id, balance FROM accounts WHERE id = 4 FOR UPDATE;
-- ...B is BLOCKED: it is waiting for the other session

A> UPDATE accounts SET balance = balance - 30000 WHERE id = 4;
UPDATE 1

A> COMMIT;
COMMIT

-- B's waiting statement finishes:
 id | balance
----+---------
 4  | 70000  
(1 row)

B> COMMIT;
COMMIT

```

**Answer:** B was blocked until A committed, then read **70000**, not the stale 100000. Reading under the lock means the balance you check is the balance you update. That is why the transfer code locks first, re-reads, then decides.

## Case 6: why the lock ORDER matters (deadlock)

A locks wallet 4 then wants 5. B locks 5 then wants 4. (`deadlock_timeout` lowered to 200ms so the lab is quick.)

```
A> BEGIN;
BEGIN

B> BEGIN;
BEGIN

A> SELECT id FROM accounts WHERE id = 4 FOR UPDATE;
 id
----
 4 
(1 row)

B> SELECT id FROM accounts WHERE id = 5 FOR UPDATE;
 id
----
 5 
(1 row)

A> SELECT id FROM accounts WHERE id = 5 FOR UPDATE;
-- ...A is BLOCKED: it is waiting for the other session

B> SELECT id FROM accounts WHERE id = 4 FOR UPDATE;
ERROR:  deadlock detected
(SQLSTATE 40P01)

-- A's waiting statement finishes:
 id
----
 5 
(1 row)

A> ROLLBACK;
ROLLBACK

B> ROLLBACK;
ROLLBACK

```

**Answer:** each waits for the other forever, so Postgres detects the cycle and kills one with `deadlock detected` (40P01). If BOTH sessions always lock the lower id first (here 4), the second one simply waits its turn and no cycle can form. That is the rule in `lockAccounts()`.
