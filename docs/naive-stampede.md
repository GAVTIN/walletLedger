# Step 2: break it first (and compare with the locked version)

Setup for every run: one wallet with **Rs 500**, then **100 concurrent transfers of Rs 10** out of it. Correct answer: exactly 50 succeed, wallet ends at Rs 0, never negative.
Generated by `npm run lab:naive`; the numbers below are what actually happened.

| Implementation | Succeeded | Stored balance | Balance computed from ledger | Reconciliation issues | Wall time | Retries |
|---|---|---|---|---|---|---|
| naive, no artificial delay | **100** / 100 | Rs 480 | **Rs -500** | NO_OVERDRAFT x1, STORED_BALANCE x1 | 763 ms | n/a |
| naive, 5 ms of app work between check and write | **100** / 100 | Rs 480 | **Rs -500** | NO_OVERDRAFT x1, STORED_BALANCE x1 | 406 ms | n/a |
| **locked: READ COMMITTED + SELECT FOR UPDATE (the real code)** | **50** / 100 | Rs 0 | **Rs 0** | none | 659 ms | 0 |
| **SERIALIZABLE, no locks, retry on 40001** | **50** / 100 | Rs 0 | **Rs 0** | none | 665 ms | **840** |

The exact stored balance of the naive runs differs every time (it depends on thread timing; I saw Rs 460, 490 and 470 across runs). What did not change in any run: all 100 transfers "succeeded" and the ledger-computed balance was Rs -500.

## What went wrong in the naive version

1. It **reads** the balance with no lock, so 100 requests all see "Rs 500" at nearly the same moment.
2. Each one passes the `balance >= amount` check against that stale number.
3. Each then **writes** `balance = 500 - 10 = 490` (a value computed from its stale read), overwriting what the others wrote. That is a **lost update**: the stored balance barely moves.
4. But every request also inserted its ledger entries, so the *ledger* says far more than Rs 500 left the wallet. The computed balance is **negative**: money was created out of nothing, and the stored balance hides it.
5. The `CHECK (balance >= 0)` constraint did not save us: the naive code never writes a negative *stored* number. That is why the nightly reconciliation job (stored vs computed) exists, and why it caught this above.

**SERIALIZABLE is also correct** here (50 succeed, balance Rs 0, books clean) and, at this small scale on a local database, its wall time is in the same range as locking. The cost shows up elsewhere: **aborted attempts**. Every `40001` is a whole transaction thrown away and re-run, and every caller must implement that retry loop correctly. With locks the same requests simply wait their turn, with zero aborts. How the waste grows with contention (all requests succeed in this experiment, so only the number of writers changes):

| Concurrent writers on ONE wallet | Total attempts for that many requests | Retries (aborted attempts) | Retries per request | Wall time |
|---|---|---|---|---|
| 5 | 15 | 10 | 2.0 | 34 ms |
| 10 | 42 | 32 | 3.2 | 95 ms |
| 25 | 164 | 139 | 5.6 | 228 ms |
| 50 | 462 | 412 | 8.2 | 459 ms |
| 100 | 1153 | 1053 | 10.5 | 983 ms |
| 200 | 2223 | 2023 | 10.1 | 1413 ms |

The locked version takes `SELECT ... FOR UPDATE` on the wallet row first, so the 100 transactions run the read-check-write sequence **one at a time**, each seeing the previous one's committed balance.
